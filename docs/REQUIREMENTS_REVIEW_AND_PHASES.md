# MyHealth — Requirements Review and Development Phases

**Source reviewed:** `docs/initial_requirements/APP_REQUIREMENTS.md` (v1.0, 2026-09-30) and `docs/initial_requirements/ios/` (HealthKit module + expected API contract).
**Scope of this delivery:** backend API only (Phase 1). Mobile apps and web dashboards are later phases.

---

## 1. Overall assessment

The document is strong on *what must never go wrong* (data isolation, versioning, attendance semantics, HealthKit honesty, professional boundaries, LGPD). It is a good foundation for a domain model because most rules are stated as verifiable invariants (e.g. "a session cannot be marked completed without the required documentation", "a partial update cannot overwrite a completed state").

It is weaker on *operational detail*: several P0 items depend on P1 items, a few rules contradict each other, and §12 leaves decisions open that change the data model (tenancy, billing owner). These are listed below with the assumption the API makes so work can proceed.

| Area | Verdict |
|---|---|
| Training core (RF-10 → RF-22) | Clear and implementable. Best-specified part of the document. |
| Identity / relationships / permissions (RF-01 → RF-05, §6) | Clear intent; the access matrix is a good basis for authorization tests. Needs a concrete list of shareable data categories. |
| HealthKit (RF-38 → RF-44, HK-01 → HK-08) | Very good; honest about HealthKit limits. Dedup key and mean definition need a decision (see 2.4). |
| Nutrition (RF-28 → RF-32) | Implementable once §12.3 (depth) is decided. Proposed "simple diary + prescribed plan" is the right MVP. |
| Therapies (RF-33 → RF-37) | Implementable but **legally gated** (qualification verification, consent text). Needs legal input before build. |
| Billing / reports (RF-47 → RF-49) | P1, correctly deferred. Depends on §12.1/12.2. |
| Non-functional (RNF-01 → RNF-10) | Correct and necessary. RPO/RTO and retention periods are undefined. |

## 2. Findings

### 2.1 Gaps and inconsistencies

1. **Numbering gap:** RF-45 and RF-46 do not exist (RF-44 → RF-47). Confirm nothing was dropped.
2. **"Next session" (RF-06, P0) vs. calendar (RF-09, P1):** a P0 home screen cannot show a *scheduled* next session without the P1 calendar. **Assumption:** in Phase 1 "next session" = the next planned session of the active plan in plan order (rotation). Therapy appointments add a real date in Phase 3.
3. **Missed workouts (§5) vs. no day-level plan in P0:** a workout is "missed" only if planned for that day, but day-of-week planning is RF-15 (P1). **Assumption:** Phase 1 reports *completed sessions* and *active days* only; "missed" is not computed until weekly planning exists. This also guarantees "rest is not an absence".
4. **Offline (RF-16, P1) vs. idempotency (RNF-09, HK-07, P0):** offline is P1 but its foundations are P0. **Decision:** every write that a phone may retry uses a client-generated stable ID from day one (workout session ID, set-log ID, heart-rate sample ID).
5. **Administrators (RF-03 vs. RF-50 vs. RNF-04):** admins must handle LGPD requests and audit access without clinical access. **Decision:** admins see metadata (who/when/what type), never clinical payloads; exports are generated by the system for the data subject, not viewed by the admin.
6. **Android (RNF-07) vs. HealthKit-only (RF-39):** heart rate on Android (Health Connect) is out of scope. The API heart-rate contract is source-agnostic so Android can be added later without changes.
7. **Shareable data categories are implicit.** §6 says "if authorized" in several cells but does not enumerate categories. **Decision:** `HeartRate`, `WorkoutSummary`, `PhysicalAssessments`, `NutritionSummary`, `TherapySummary`. Grants are per relationship and per category, with history.
8. **"Role used" for multi-role users** (§2) — **decision:** a user may hold one professional profile per discipline; each professional record stores the *profile* id (trainer/dietitian/practitioner), not only the user id.
9. **Time zones:** attendance counts on the *client's local date* (§5), so the client's IANA time zone must be captured at onboarding and the session must store the zone it was performed in.
10. **Units:** not specified. **Decision:** SI units in the API (kg, metres, seconds, bpm); the apps localise.

### 2.2 Ambiguities resolved by assumption (to be confirmed)

| # | Topic | Assumption used by the API |
|---|---|---|
| A1 | Market (§12.1) | Independent professionals first; the model is tenancy-ready (organisations are RF-05, P1). |
| A2 | Invitations (RF-01) | A verified professional invites by e-mail; the client accepts after signing up with that e-mail. |
| A3 | Verification (RF-04) | An administrator verifies registration (e.g. CREF/CRN) manually; only *verified* professionals can invite, publish or provide care. Changing the registration resets verification. |
| A4 | Feedback (RF-19) | Perceived exertion (1–10) is required to complete; discomfort and comments are optional. |
| A5 | Plan editing after publish | The plan keeps an editable *draft*; each publish creates an immutable numbered version. Executions reference the version. |
| A6 | Corrections (§5 History) | Phase 1 allows set-log corrections only while the session is in progress; post-completion corrections with reason come in Phase 2. |

### 2.3 Risks

- **Legal (blocking for Phase 3):** acupuncture scope (the document cites Law 15,345/2026 — must be validated by legal counsel), consent wording, council rules (CREF, CRN, COFFITO/CFM etc.).
- **Regulatory:** RNF-10/Anvisa — keep every heart-rate feature descriptive (no alerts that look like diagnosis). The API exposes raw samples and descriptive statistics only, labelled with method and provenance.
- **Privacy (RNF-01):** legal basis per purpose is undefined. The API records *grants* (who may see what, since when) but the legal-basis catalogue is a product/legal deliverable.
- **Undefined targets:** RPO/RTO (RNF-05), retention periods (§12.5), heart-rate update frequency (§12.6).

### 2.4 iPhone / HealthKit integration — findings and resolutions ✅

Current focus. Every item below is implemented on both sides of the contract (API and the reference Swift module in
`docs/initial_requirements/ios`) and covered by tests (`IphoneIntegrationTests`, `HeartRateTests`, `IphoneContractTests`, `WorkoutHeartRateTests`).

| # | Finding (gap or contradiction) | Resolution |
|---|---|---|
| H1 | **Dedup key contradiction:** README `(client, healthKitID)` vs. RF-42 "source id, type, interval"; the first API version used `(session, UUID)`. | Follow the README: unique per **client** + HealthKit UUID (DB unique index). The HealthKit UUID already identifies source, type and interval. A sample already stored for another session is reported as `claimedByOtherSession`. |
| H2 | **Mean contradiction:** the phone sends an arithmetic mean; the README says a physiological average must be time-weighted; §12.6 left it open. | Store **both**: `averageBeatsPerMinute` (arithmetic, comparable with the phone) and `timeWeightedAverageBeatsPerMinute` (trapezoidal, excludes gaps over 60 s, null when samples are too sparse), each with its method name. Phone values are ignored. |
| H3 | **HK-06 gap:** nothing prevented a second Apple Health workout after a retry, reinstall or second device; the server did not know about the opt-in. | Opt-in stored server-side (`PUT …/apple-health/workout-saving`), independent of import (iOS write permission is separate). The phone reports the saved HKWorkout (`PUT …/apple-health-workout`): first id wins, a different id → 409. The Swift module now checks for an existing workout with the same `HKMetadataKeyExternalUUID` before saving. Covers acceptance test 12. |
| H4 | **HK-08 gap:** the module does one final query; there was no way to know *which* workouts to reconcile, nor an "authorized period". | `GET …/apple-health/reconciliation` lists finished workouts within a **30-day** window (empty unless import is connected); Swift `reconcile(workoutID:startedAt:endedAt:)` rebuilds the authoritative report. Samples recorded while import was **paused or revoked** are rejected even if uploaded later; uploads after the window → 409. |
| H5 | **RF-43 contradiction:** "revocation stops new reads *and sharing*" vs. the first version, which kept professional access after revoking Apple Health. | Revoking Apple Health stops professional access (`HealthData.SharingStopped`) even with an active grant, hides recipients, and turns off workout saving. The client keeps their own data. Pause stops import only. |
| H6 | **RF-43 gap:** every sample was labelled "measured", but Apple Health also holds values typed in by people. | Points carry `wasUserEntered` (`HKMetadataKeyWasUserEntered`); the API labels each point `measured` / `self-reported`, the record `measured` / `self-reported` / `mixed`, and counts self-reported samples in the summary. |
| H7 | **Session id contradiction:** README says "use the stable session ID from the backend" but offline start (RNF-09) needs an id before any network call. | The phone generates the id and registers it with idempotent `POST /workout-sessions` before starting HealthKit. README updated. |
| H8 | **Swift bug:** `.iso8601` encoding drops fractional seconds, so a sample in the first second can fall before the session start and be rejected. | Encoder now writes ISO 8601 with fractional seconds. |
| H9 | **Swift gap:** every non-2xx was a retryable `uploadFailed`, so a permanent 403 (import paused) or 404 would be retried forever. | `uploadFailed` (network, 408, 409, 429, 5xx) vs. `uploadRejected(statusCode)` (other 4xx, do not retry). |
| H10 | **Ordering (HK-07):** the README order is finish → complete → upload, but retries can reorder. | A final report is accepted before API completion; completion still succeeds afterwards; a late in-progress report after the final one is ignored as stale. |
| H11 | **"Without connection":** status was null before connecting, which the app could not tell apart from an error. | Explicit `NotConnected` status. |

Unchanged decisions: snapshot semantics (in-progress additive, final authoritative, source deletions kept as *removed*),
plausibility 20–300 bpm inside the server's session interval, uploads refused while import is paused or revoked.

Still open (product decision, not blocking): expected upload cadence during workouts (§12.6) — the API is cadence-agnostic.
