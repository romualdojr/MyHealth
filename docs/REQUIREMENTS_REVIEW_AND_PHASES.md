# MyHealth — Requirements Review and Development Phases

**Source reviewed:** `docs/initial_requirements/APP_REQUIREMENTS.md` (v1.0, 2026-09-30) and `docs/initial_requirements/ios/` (HealthKit module + expected API contract).
**Scope of this delivery:** backend API only (Phases 0–3). Mobile apps and web dashboards are later phases.

---

## 1. Overall assessment

The document is strong on *what must never go wrong* (data isolation, versioning, attendance semantics, HealthKit honesty, professional boundaries, LGPD). It is a good foundation for a domain model because most rules are stated as verifiable invariants (e.g. "a session cannot be marked completed without the required documentation", "a partial update cannot overwrite a completed state").

It is weaker on *operational detail*: several P0 items depend on P1 items, a few rules contradict each other, and §12 leaves decisions open that change the data model (tenancy, billing owner). These are listed below with the assumption the API makes so work can proceed.

| Area | Verdict |
|---|---|
| Training core (RF-10 → RF-22) | Clear and implementable. Best-specified part of the document. |
| Identity / relationships / permissions (RF-01 → RF-05, §6) | Clear intent; the access matrix is a good basis for authorization tests. Needs a concrete list of shareable data categories. |
| HealthKit (RF-38 → RF-44, HK-01 → HK-08) | Very good; honest about HealthKit limits. Dedup key and mean definition need a decision (see 2.4). |
| Nutrition (RF-28 → RF-32) | Implementable once §12.3 (depth) is decided. Proposed "simple diary + prescribed plan" is the right MVP. |
| Therapies (RF-33 → RF-37) | Implementable but **legally gated** (qualification verification, consent text). Needs legal input before build. |
| Billing / reports (RF-47 → RF-49) | P1, correctly deferred. Depends on §12.1/12.2. |
| Non-functional (RNF-01 → RNF-10) | Correct and necessary. RPO/RTO and retention periods are undefined. |

## 2. Findings

### 2.1 Gaps and inconsistencies

1. **Numbering gap:** RF-45 and RF-46 do not exist (RF-44 → RF-47). Confirm nothing was dropped.
2. **"Next session" (RF-06, P0) vs. calendar (RF-09, P1):** a P0 home screen cannot show a *scheduled* next session without the P1 calendar. **Assumption:** in Phase 1 "next session" = the next planned session of the active plan in plan order (rotation). Therapy appointments add a real date in Phase 3.
3. **Missed workouts (§5) vs. no day-level plan in P0:** a workout is "missed" only if planned for that day, but day-of-week planning is RF-15 (P1). **Assumption:** Phase 1 reports *completed sessions* and *active days* only; "missed" is not computed until weekly planning exists. This also guarantees "rest is not an absence".
4. **Offline (RF-16, P1) vs. idempotency (RNF-09, HK-07, P0):** offline is P1 but its foundations are P0. **Decision:** every write that a phone may retry uses a client-generated stable ID from day one (workout session ID, set-log ID, heart-rate sample ID).
5. **Administrators (RF-03 vs. RF-50 vs. RNF-04):** admins must handle LGPD requests and audit access without clinical access. **Decision:** admins see metadata (who/when/what type), never clinical payloads; exports are generated by the system for the data subject, not viewed by the admin.
6. **Android (RNF-07) vs. HealthKit-only (RF-39):** heart rate on Android (Health Connect) is out of scope. The API heart-rate contract is source-agnostic so Android can be added later without changes.
7. **Shareable data categories are implicit.** §6 says "if authorized" in several cells but does not enumerate categories. **Decision:** `HeartRate`, `WorkoutSummary`, `PhysicalAssessments`, `NutritionSummary`, `TherapySummary`. Grants are per relationship and per category, with history.
8. **"Role used" for multi-role users** (§2) — **decision:** a user may hold one professional profile per discipline; each professional record stores the *profile* id (trainer/dietitian/practitioner), not only the user id.
9. **Time zones:** attendance counts on the *client's local date* (§5), so the client's IANA time zone must be captured at onboarding and the session must store the zone it was performed in.
10. **Units:** not specified. **Decision:** SI units in the API (kg, metres, seconds, bpm); the apps localise.

### 2.2 Ambiguities resolved by assumption (to be confirmed)

| # | Topic | Assumption used by the API |
|---|---|---|
| A1 | Market (§12.1) | ~~Independent professionals first; organisations later.~~ Superseded by §4.1.1 (SaaS): every professional works inside a tenant from day one — see 2.6. |
| A2 | Invitations (RF-01) | A verified professional invites by e-mail; the client accepts after signing up with that e-mail. |
| A3 | Verification (RF-04) | An administrator verifies registration (e.g. CREF/CRN) manually; only *verified* professionals can invite, publish or provide care. Changing the registration resets verification. |
| A4 | Feedback (RF-19) | Perceived exertion (1–10) is required to complete; discomfort and comments are optional. |
| A5 | Plan editing after publish | The plan keeps an editable *draft*; each publish creates an immutable numbered version. Executions reference the version. |
| A6 | Corrections (§5 History) | Sets are overwritten while the session is in progress; after it ends, corrections need a reason and keep the previous values (done in Phase 2, see 2.7 N15). |

### 2.3 Risks

- **Legal (blocking the go-live of Phase 3, not its build — see 2.8):** acupuncture scope (the document cites Law 15,345/2026 — must be validated by legal counsel), consent wording, council rules (CREF, CRN, COFFITO/CFM etc.).
- **Regulatory:** RNF-10/Anvisa — keep every heart-rate feature descriptive (no alerts that look like diagnosis). The API exposes raw samples and descriptive statistics only, labelled with method and provenance.
- **Privacy (RNF-01):** legal basis per purpose is undefined. The API records *grants* (who may see what, since when) but the legal-basis catalogue is a product/legal deliverable.
- **Undefined targets:** RPO/RTO (RNF-05), retention periods (§12.5), heart-rate update frequency (§12.6).

### 2.4 iPhone / HealthKit integration — findings and resolutions ✅

Every item below is implemented on both sides of the contract (API and the reference Swift module in
`docs/initial_requirements/ios`) and covered by tests (`IphoneIntegrationTests`, `HeartRateTests`, `IphoneContractTests`, `WorkoutHeartRateTests`).

| # | Finding (gap or contradiction) | Resolution |
|---|---|---|
| H1 | **Dedup key contradiction:** README `(client, healthKitID)` vs. RF-42 "source id, type, interval"; the first API version used `(session, UUID)`. | Follow the README: unique per **client** + HealthKit UUID (DB unique index). The HealthKit UUID already identifies source, type and interval. A sample already stored for another session is reported as `claimedByOtherSession`. |
| H2 | **Mean contradiction:** the phone sends an arithmetic mean; the README says a physiological average must be time-weighted; §12.6 left it open. | Store **both**: `averageBeatsPerMinute` (arithmetic, comparable with the phone) and `timeWeightedAverageBeatsPerMinute` (trapezoidal, excludes gaps over 60 s, null when samples are too sparse), each with its method name. Phone values are ignored. |
| H3 | **HK-06 gap:** nothing prevented a second Apple Health workout after a retry, reinstall or second device; the server did not know about the opt-in. | Opt-in stored server-side (`PUT …/apple-health/workout-saving`), independent of import (iOS write permission is separate). The phone reports the saved HKWorkout (`PUT …/apple-health-workout`): first id wins, a different id → 409. The Swift module now checks for an existing workout with the same `HKMetadataKeyExternalUUID` before saving. Covers acceptance test 12. |
| H4 | **HK-08 gap:** the module does one final query; there was no way to know *which* workouts to reconcile, nor an "authorized period". | `GET …/apple-health/reconciliation` lists finished workouts within a **30-day** window (empty unless import is connected); Swift `reconcile(workoutID:startedAt:endedAt:)` rebuilds the authoritative report. Samples recorded while import was **paused or revoked** are rejected even if uploaded later; uploads after the window → 409. |
| H5 | **RF-43 contradiction:** "revocation stops new reads *and sharing*" vs. the first version, which kept professional access after revoking Apple Health. | Revoking Apple Health stops professional access (`HealthData.SharingStopped`) even with an active grant, hides recipients, and turns off workout saving. The client keeps their own data. Pause stops import only. |
| H6 | **RF-43 gap:** every sample was labelled "measured", but Apple Health also holds values typed in by people. | Points carry `wasUserEntered` (`HKMetadataKeyWasUserEntered`); the API labels each point `measured` / `self-reported`, the record `measured` / `self-reported` / `mixed`, and counts self-reported samples in the summary. |
| H7 | **Session id contradiction:** README says "use the stable session ID from the backend" but offline start (RNF-09) needs an id before any network call. | The phone generates the id and registers it with idempotent `POST /workout-sessions` before starting HealthKit. README updated. |
| H8 | **Swift bug:** `.iso8601` encoding drops fractional seconds, so a sample in the first second can fall before the session start and be rejected. | Encoder now writes ISO 8601 with fractional seconds. |
| H9 | **Swift gap:** every non-2xx was a retryable `uploadFailed`, so a permanent 403 (import paused) or 404 would be retried forever. | `uploadFailed` (network, 408, 409, 429, 5xx) vs. `uploadRejected(statusCode)` (other 4xx, do not retry). |
| H10 | **Ordering (HK-07):** the README order is finish → complete → upload, but retries can reorder. | A final report is accepted before API completion; completion still succeeds afterwards; a late in-progress report after the final one is ignored as stale. |
| H11 | **"Without connection":** status was null before connecting, which the app could not tell apart from an error. | Explicit `NotConnected` status. |

Unchanged decisions: snapshot semantics (in-progress additive, final authoritative, source deletions kept as *removed*),
plausibility 20–300 bpm inside the server's session interval, uploads refused while import is paused or revoked.

Still open (product decision, not blocking): expected upload cadence during workouts (§12.6) — the API is cadence-agnostic.

### 2.6 Multi-tenant SaaS (§4.1.1, MT-01 → MT-10) — findings and resolutions ✅

The requirements now make tenancy P0 (RF-05 moved from P1). The Phase 1 API was **not** multi-tenant: it isolated
data per professional and per client only, with no organization concept. Gaps found and how they were resolved
(details in `docs/ARCHITECTURE.md` → *Multi-tenancy*):

| # | Gap in the Phase 1 API | Resolution |
|---|---|---|
| T1 | No tenant or membership model; professional roles were global (MT-01/02). | `Tenant` + `TenantMembership` (disciplines, tenant-admin flag, invite → accept, revoke). `POST /tenants` creates one with the caller as administrator. Credentials (`ProfessionalProfile`) stay global and are verified once. |
| T2 | No record carried a tenant id; the API could not tell which organization owned a plan, session or relationship (MT-04). | `tenant_id` (+ FK) on relationships, plans, versions, sessions, heart rate, custom exercises; nullable on notifications and audit. Inherited along plan → version → session → heart rate, never taken from input. |
| T3 | No active-tenant context; queries filtered by user only (MT-02/05/07). | `X-Tenant-Id` selects the tenant, honoured only for an active membership (`ITenantContext`). `ICareAccess` and every professional query/command filter by tenant and profile. |
| T4 | A professional with a heart-rate grant could list heart rate from **every** workout of the client, including workouts prescribed elsewhere (MT-06). | Shared heart-rate reads are limited to workouts of the relationship's tenant. |
| T5 | Custom exercises were readable by anyone with the id. | Custom exercises belong to a tenant; readable by its members and by its clients; other tenants get 404 and cannot prescribe them. |
| T6 | One "Administrator" role mixed platform operation with organization management (MT-05, RF-50). | Platform administrator (credential verification, tenant list, cross-tenant audit, no tenant access) vs. tenant administrator (members, tenant audit, no clinical access). |
| T7 | Nothing happened to access when a professional left an organization (MT-08). | Revoking the membership ends their relationships in that tenant in the same transaction; records stay. Last administrator cannot be removed. |
| T8 | Cross-tenant attempts were not audited (MT-09). | `deny` audit entries (tenant id, no subject) for unknown-tenant headers and known ids from another tenant. Covered by `MultiTenancyTests` (acceptance tests 14 and 15). |
| T9 | Notifications had no tenant, so a professional saw every organization's alerts together (MT-07). | Notifications carry tenant and audience; professional ones are listed only in their tenant's context, client ones in the client view. |

Open points for the business/product (not blocking):

- **RF-05 "each independent professional *receives* a dedicated organization":** the API lets the professional create
  it (`POST /tenants`, kind `SoloPractice`) instead of creating one automatically with the profile, because someone
  joining a clinic should not get an unused solo practice. Confirm the onboarding flow.
- **RF-05 reassignment and transfer audit trail** (moving a client between professionals of a tenant) is not yet built.
- **MT-07/MT-09 files, exports, background jobs:** those features do not exist yet; they must use the same tenant checks.
- **Tenant suspension** (unpaid subscription) depends on billing (§12.2).

### 2.7 Phase 2 — assessments, nutrition, privacy: findings and resolutions ✅

Gaps and contradictions found while building RF-23 → RF-25, RF-28 → RF-30, RNF-04, RF-50 and RNF-02, and how the API
resolves them. Items marked **(confirm)** are product or legal calls the API had to make to proceed.

| # | Finding | Resolution |
|---|---|---|
| N1 | **Who may see the health history?** §3 journey 2 has the trainer review it, but §6 has no row for it and the category list (2.1 #7) had none. | New `HealthHistory` data category. *Every* professional, trainers included, reads it only with the client's grant; reads are audited. **(confirm)** that trainers should not get it by default. |
| N2 | **"Significant changes flag the prescription for review" (RF-23)** — "significant" is undefined. | Changes to *limitations* or *reported injuries* are significant; goals, availability and equipment are not. Open training plans are flagged only for trainers the client shares the history with (active relationship + `HealthHistory` grant), because even "something changed" is health information; the reason text names no condition. The trainer is notified and clears the flag by acknowledging or publishing a new version; the dashboard counts flagged plans. **(confirm)** the list of significant fields. |
| N3 | **RF-23 "acknowledgment"** — of what? | Each submission must confirm the information is true and complete (`acknowledged = true`); the time is stored on the revision. Identical resubmissions are no-ops, so retries do not create revisions. |
| N4 | **"Do not compare different methods" (RF-24)** needs a model. | Every measurement is *(metric, method, unit, value)*. Series in My Progress are grouped by all three, so body fat by bioimpedance and by skinfolds are separate lines. Units are a fixed SI/clinical list (2.1 #10). Only recorded points are returned — no interpolation. |
| N5 | **Photos in RF-24 and RF-30** need file storage, which is RF-27 (P1), with the tenant checks of MT-07/MT-09. | Not accepted yet. They arrive with the files feature; the records already have the place for them conceptually (assessment/diary entry ids). |
| N6 | **Which dietitian sees a diary entry?** A client may have dietitians in several organizations, and MT-10 forbids automatic cross-tenant sharing. | Each entry is *addressed*: logged against a meal plan (→ its dietitian and tenant) or a dietitian relationship; otherwise it is private. Tenant and dietitian are derived server-side, never from input. Only that dietitian reads and comments, while the relationship is active. |
| N7 | **§9 "trainers see only what the client *and dietitian* authorize".** | Implemented as the client's `NutritionSummary` grant on the trainer's relationship. The summary is active meal plans and last-7-days adherence *counts* from the same organization — no foods, assessments or diary text. A dietitian-side veto is **(confirm)**: it needs a product decision. |
| N8 | **§12.3 nutrition depth.** | The recommended MVP: prescribed, versioned meal plan + simple diary. No nutrient database or calculations (RF-31, P1). |
| N9 | **RF-29 "only a qualified dietitian may prescribe".** | Creating, editing and publishing need a verified dietitian profile acting in a membership that includes the discipline; suspension stops publishing immediately (acceptance test 7, nutrition part). |
| N16 | **Suspension (RF-50) only blocked writes:** reads kept working because they accept unverified profiles (a registration change resets verification). | *Suspended* or *rejected* profiles lose all care access, reads included, in `ICareAccess` — direct and shared. A profile *pending* re-verification keeps read access to existing clients but cannot prescribe. |
| N10 | **RNF-04 export: what is "their records" and "no third-party data"?** | Records whose *subject* is the caller, from every tenant, with provenance (organization, responsible professional, method, timestamps, sources). A professional exporting their own data gets their profile and memberships, never their clients' records. Professionals are named only by public display name; other actors in the access log are described by role. Drafts are excluded. |
| N11 | **RNF-04 correction and deletion "subject to retention obligations".** | A request workflow: the user submits, a platform operator starts, completes or rejects (a rejection needs a reason, e.g. a legal retention period) and the user is notified. Changes themselves are applied by the operator; automatic deletion waits for the retention decisions (§12.5). |
| N12 | **RF-50 "configure retention"** while periods are undefined (2.3). | A retention catalogue per record type (period in months, legal basis, notes), editable by operators and audited. It is recorded, **not yet enforced** — no purge job until legal counsel sets the periods. |
| N13 | **RNF-02 MFA** with bearer tokens: refreshed tokens lose Identity's `amr` claim. | Enforcement checks that the *account* has two-factor enabled (Identity then refuses any sign-in without it). Applies to every tenant action and every `/admin` endpoint; client views are exempt. Relaxed only in `appsettings.Development.json`. |
| N14 | **Push/e-mail providers are undecided (§8).** | Transactional outbox with logging placeholders behind `IPushSender` / `INotificationEmailSender`. Push goes to all registered devices; e-mail only when the person has no device, to avoid duplicate alerts. Texts never contain clinical content. |
| N15 | **A6 (post-completion corrections).** | Done: after a workout ends the client corrects a set with a reason; previous values, reason and person are kept on the set and the change is audited. During the workout, sets are still simply overwritten. |

Not in Phase 2 (unchanged scope): RF-07 configurable reminders, RF-26 goals (My Progress shows the goals professionals
already define: training plan goal, meal plan goal, latest nutrition assessment goals), RF-27 files, RF-31/32.

### 2.8 Phase 3 — therapies: findings and resolutions ✅

The legal review (2.3) gates *going live*, not building. Everything it decides is configuration a platform operator
enters, so the code does not change when the lawyers answer.

| # | Finding | Resolution |
|---|---|---|
| R1 | **Who may practise acupuncture (§9, Law 15,345/2026)** is a legal answer, not a code constant. | Each `TherapyModality` lists its *accepted councils* (e.g. CFM, COFFITO). Acupuncture is seeded **disabled with none**. An operator enables a modality only with accepted councils **and** a legal-review reference (stored with who enabled it and when). Changing councils, required fields or the consent rule on an enabled modality disables it again for re-review. |
| R2 | **RF-33 "verify qualifications and permitted scope for each modality".** | `PractitionerQualification` (training title, issuer, certificate) per practitioner and modality, global like the council registration. Operators verify it, and verification fails when the practitioner's council is outside the modality's scope. Services, scheduling, documentation, completion and care plans all require: verified profile + enabled modality + council in scope + verified qualification. Revoking a qualification stops care at once. |
| R3 | **RF-34 "points or regions *when relevant*"** — and which fields are mandatory at all? | The modality lists its required record fields. Acupuncture's default: concern, assessment, contraindications/precautions, technique, duration, adverse events, post-session guidance — points/regions optional. "None" must be written explicitly (an empty adverse-events field is indistinguishable from a forgotten one). **(confirm)** the list. |
| R4 | **RF-35 consent "with version"** — what happens when the text changes? | Operators publish numbered, immutable `ConsentTemplate` versions (text + disclosed risks). The client decides in the app on the version they read; the decision copies the risks. Completion requires a granted, not withdrawn consent by that client, for that practitioner, tenant and modality, **on the current version** — a new version means consenting again. Refusals and withdrawals are recorded. **(confirm)** that re-consent on every new version is wanted; in-person paper consent is not modelled. |
| R5 | **RF-35 "cannot be marked completed without the required documentation".** | `Complete` fails with `MissingDocumentation` (naming the fields) or `ConsentRequired`; the session view shows the missing fields and whether consent is in force. Acceptance test 8. |
| R6 | **RF-36 "referral for medical care when warning signs arise"** must not look like a diagnosis (RNF-10). | The practitioner records a referral (reason, routine/urgent) on the session or closes the care plan with outcome *refer for medical care*. The client gets a notification whose text says only that there is an important note. No automatic triggers. |
| R7 | **RF-36 appointments vs. RF-09 calendar (P1).** | Practitioner books, reschedules and cancels; the client can cancel. Overlapping sessions of a practitioner are refused across tenants (without revealing the other booking), enforced by a database exclusion constraint. Confirmation, reminders and cancellation policies stay in RF-09. |
| R8 | **§6 "therapy record: client views".** | Clients see their full record, guidance, corrections and referrals, and report how they feel (1–5) after a completed session. Trainers and dietitians see only a `TherapySummary` (active modalities, next appointment, recent session count) with the client's grant, inside the same organization. |
| R9 | **History (§5).** | Completed records change only through corrections that keep the previous record, reason and practitioner. Referrals are appended, never replaced. Until completion the record is the practitioner's work in progress: clients see it, and the export includes it, only once the session is completed. |
| R10 | **Review findings (independent review of the Phase 3 diff).** | Eligibility is re-checked on *every* care action, including rescheduling, care-plan reviews and re-activating a service (only a medical-care referral is exempt). Ending a relationship — by either side or because the practitioner left the organization — cancels its scheduled sessions and notifies the client. Double booking is prevented by a PostgreSQL exclusion constraint (`btree_gist`; the extension must be allowed on the production server), not only by the application check. Known service ids from other tenants are audited as `deny`. |

Not in Phase 3: RF-37 other modalities need their own legal review, but the same model supports them (operators add a
modality); in-person/paper consent capture; reminders.

### 2.9 Platform billing — who pays MyHealth: findings and resolutions ✅

§12.1/12.2 left the commercial model open. Decided for this phase: **organizations and solo practices pay MyHealth,
priced per module**; payments go through a provider abstraction with a fake implementation until one is chosen. How
professionals charge their own clients (RF-47 in the client sense) is a separate, later question.

| # | Finding | Resolution |
|---|---|---|
| B1 | What is a "module", and what does a tenant pay for? | Three modules that map one-to-one to disciplines: Training, Nutrition, Therapies. A tenant pays the sum of its subscribed modules' monthly prices. Prices are effective-dated; an invoice snapshots the price per line, so later changes never alter issued invoices. A module without a price is never invoiced (the cycle reports it). **(confirm)** real prices; placeholders are seeded. |
| B2 | How does a new tenant start? | A 30-day trial with every module available; its chosen disciplines become its paid modules. Operators can extend a trial, change modules or end the trial early by issuing the first invoice. Existing tenants received the same trial in the migration. **(confirm)** trial length. |
| B3 | Billing period and due date. | Monthly, prepaid: the invoice for a period is issued when it starts and is due 5 days later. **(confirm)** due and grace days. |
| B4 | What does non-payment do? | Past due on the due date (a banner, nothing blocked); suspended after a 10-day grace period. Suspension blocks professional work in that tenant (`Tenant.Suspended`), not administration or billing, so the tenant can still pay; clients keep access to their own records (RNF-04). Paying everything overdue reactivates automatically, except an operator's manual suspension. |
| B5 | Module gating. | After the trial, a professional whose discipline's module is not subscribed is refused with `Tenant.ModuleNotSubscribed`. |
| B6 | Payment confirmation (RF-48). | Through the provider's signed webhook only (or an operator's audited offline payment). Each provider event is processed once (unique provider + event id); an amount that differs from the invoice is recorded and not applied. Charges are Pix-first, reused until they expire. |
| B7 | Who operates billing? | MyHealth's operators, in a separate back-office app (not the organization dashboard), with every action requiring a reason or note and kept in the subscription history. |
| B8 | Brazilian invoicing (NF-e/NFS-e) and taxes. | Out of scope here: invoices are internal charges, not fiscal documents. **(decide)** the fiscal-document provider together with the payment provider. |

### 2.10 Client experience: assistant, rest-time questions, exercise video — findings and resolutions ✅

From the client prototype: entering everything by hand is too much for clients, so the app asks small questions at
the right moment and an assistant turns what they say into records.

| # | Finding | Resolution |
|---|---|---|
| C1 | An assistant sends health data to an AI provider (LGPD sensitive data). | Separate, versioned consent with chosen areas (training, nutrition, therapies), withdrawable; only the consented areas and recent records go into each request; each message audited. **(decide)** the provider and sign a data processing agreement before enabling `Anthropic` in production. |
| C2 | The assistant must not practise health care (RNF-10). | Fixed rules in the system prompt; it can only *prepare* records through three tools, and nothing is saved without the client's confirmation. Pain becomes a report to the trainer with server-defined safety text. It never accepts consent terms. |
| C3 | Records made by the assistant must follow the same rules as the forms. | Confirming runs the existing command as the client (same access checks, sharing, notifications, idempotency). |
| C4 | "Every exercise needs a video" (RF-12 media). | Several media items per exercise (loop per angle, full video with captions and chapters, images) from the MyHealth media host only; text description required first. **(decide)** who films or licenses the library videos; upload and CDN are pending (RF-27). |
| C5 | Rest time can be used for questions, but must not disturb the workout. | The server lists at most four pending questions with who receives each answer; the phone shows one per rest, never in the last 15 s, after the heart rate drops, always skippable. |
| C6 | Sleep and energy are new health data. | `Wellbeing` sharing category (off unless the client grants it), in the data export. **(confirm)** the scales (1–5) and whether mood or stress should be added. |
| C7 | A pain answer must not be interpreted. | Body checks record better / same / worse / new and notify the trainer only when the client chooses to report. |
